# Codex Feishu Bridge

把飞书消息填入 Prompt，交给这台 Mac 上的 Codex 处理，并向原消息回复结果。

## 简化后的结构

- **任务**：查看收到的任务、执行状态和结果。
- **连接**：管理消息来源与 Codex 项目的对应关系。
- **飞书**：描述用途并创建助手，或管理已有机器人、群与处理规则。

新飞书消息 → `{{message}}` 替换 → 同一个 Codex 任务连续处理 → 文字回复。
接收器会在任务 Prompt 末尾附上来源消息 ID、会话 ID 和应用 ID，供业务 Skill 将附件发回准确的原会话；这些字段不改变模板中 `{{message}}` 恰好一次的要求。

### 连续私聊

私聊默认接着前文聊，连续发送的图片、文件和文字也进入同一个 Codex 会话。每条消息仍有独立任务记录，不改写已完成的任务，也不重复发送旧结果。对话按机器人应用、连接、私聊和发送者隔离；群聊不带入私聊历史。

更新后的第一条跟进会读取同一私聊此前被拆散的历史资料（最多最近 100 条接收记录），只作上下文，不重新执行旧操作。发送完整的一条“新对话”、“重新开始对话”或 `/new` 可开始新会话。普通群的新请求仍分别建立任务，明确回复按已有群协作规则接续。

文字和 Word、PDF 等文件一起发送时，飞书可能把它们组合成富文本消息。Bridge 同时提取文字、内嵌图片和随附文件，下载成功后一起交给助手。飞书在线文档链接仍需机器人拥有对应文档的访问权。
处理步骤、使用哪些 Skill、何时询问用户，都由 Prompt 决定。插件不再内置群流程、
审核卡片、卡片回调或分阶段工作流。付费操作的防重复与产物校验需由执行这些操作的
业务 Skill 自行负责；Bridge 仅对消息接收、任务提交和回复提供稳定请求标识。

旧版任务和数据库保留只读，既不重放也不继续旧流程。继续新工作请发送一条新的飞书消息。
新版本创建的任务支持通过回复原消息继续同一任务；前一轮完成后才提交后续消息。

## 交给你的 Agent 安装

把完整插件包交给 Agent，说：“帮我安装并接入飞书，创建助手管理员，再用一条非敏感测试消息验收。”
Agent 先读包内 `AGENTS.md` 与接入 Skill，自动检查环境、准备依赖、安装后台服务，继续发起官方扫码。
用户只完成自己的登录、扫码、企业选择和必要审批；不用复制 App Secret、填写连接或写 Prompt。
当前执行依赖已登录的 Codex 和 macOS；其他 Agent 可通过包内命令协助接入，并不替代 Codex 执行。

给 Agent 的入口：`./scripts/bridge-setup doctor`、`prepare`、`install`、`manager`。
返回机器可读的下一步；重复运行复用环境与创建记录。新安装默认自由协作，既有安装保持原设置。
安装就绪、机器人连接成功和第一条任务实际完成分别验收，不能用健康检查代替消息交付。

## 安装运行

需要 macOS、Python 3.13、已安装并登录的 Codex CLI。
使用“创建助手”还需要 Node.js 和 [飞书官方 lark-cli](https://github.com/larksuite/cli)。
已有飞书应用仍可直接接入。
Codex 在宿主机执行，当前没有 Docker 部署脚本。

```sh
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
npm ci --ignore-scripts
./run.sh
```

打开 http://127.0.0.1:8797/panel 。程序自动读取本机 Codex 项目。
可选的 `projects.json` 使用 `{ "项目名": "/absolute/project/path" }`，该文件属于本机配置，不提交到 Git。

## 创建助手

在“飞书”页点击“创建助手”，描述想让它做什么，选择私聊或群聊，然后点击“创建并配置”。

1. Codex 根据用途生成助手名称和具体处理规则，沿用本机保存的默认模型。
2. 页面显示飞书官方二维码，由本人扫码选择企业并确认创建。基础文档、表格、上传与消息权限一起申请；企业审批仍需在飞书完成。
3. Bridge 自动保存独立凭证、创建独立工作目录及连接，并保存含一处 `{{message}}` 的 Prompt。私聊默认仅开放给创建者。
4. 群聊模式再将机器人添加到目标群，由创建者 @机器人发送页面上的配对文字；完成后群内成员均可 @它使用。
5. 点击“打开飞书使用”发消息，页面显示实际任务和回复状态。“已配置”不代表第一条消息已经执行成功。

不需要手工复制 App ID、App Secret 或编写 Prompt。工作位置可在“更多选项”中选择已有项目。
“高级设置”可继续调整规则与范围；已有应用、连接、项目和历史任务保留原样。

创建记录、二维码与凭证保存在本机私有状态目录。刷新会恢复原进度；失败后“继续配置”复用已取得的凭证。
若创建结果无法确认，先核对飞书是否已有该机器人，避免重新扫码生成重复应用。
关闭服务会中断未完成的扫码，请保持 Bridge 运行到配置完成。
自动生成的规则不等于新增权限；旧文档访问、额外平台账号或其他业务能力仍需按实际任务核实。

## 在飞书创建和管理助手

首次使用，推荐先在“飞书”页顶部点击 **“创建助手管理员”**。不用填写用途、App ID、App Secret、项目或 Prompt。

1. 点击“创建助手管理员”。
2. 用自己的飞书扫码，确认所属企业和创建。
3. Bridge 自动保存独立凭证、创建工作位置、连接机器人并写入管理规则。
4. 页面变为“助手管理员已就绪”，点击“打开助手管理员”，在飞书私聊说出需求即可。

创建过程中刷新页面会恢复当前步骤。已经有管理员时，快捷入口直接打开原机器人；已移除时显示“恢复助手管理员”，不会重复创建。管理员只申请消息收发权限。

分享给其他人时，分发插件源码及安装说明即可。对方需要在自己的 Mac 上安装上述依赖并登录 Codex，运行后使用这个入口和自己的飞书扫码。各自的凭证、工作目录、机器人和管理身份独立保存在各自电脑上；不要把 `.env`、`data/`、数据库、本机凭证或备份目录打包分享。当前任务执行依赖 Codex；其他 Agent 也可以打开本机网页使用面板，安装入口由其支持的插件方式决定。

只接受扫码创建者的私聊，群聊和其他用户的消息不会触发管理操作。

向它发送自然语言即可：

- “帮我创建一个读书笔记助手，我自己私聊用，把阅读材料整理为飞书文档。”
- “查看我的助手和创建进度。”
- “把读书笔记助手的用途改为整理会议纪要并提取待办。”
- “继续配置读书笔记助手。”
- “移除读书笔记助手。” / “恢复读书笔记助手。”

Bridge 的助手卡片也提供“移除助手”。移除会停用该助手的本机接入与连接，保留历史任务、工作文件和飞书应用；可从“已移除的助手”恢复。尚有未结束任务、待处理消息或未发送结果时拒绝移除，避免中断交付。管理员只能移除自己创建的助手；管理机器人自身可在本机页面移除和恢复。此功能不注销飞书云端应用。

创建时会先确认收到，再回复官方确认链接；本人确认后自动接入并回复使用入口。
群聊助手仍需加群和由扫码者发送配对文字。审批未生效时保留进度，之后可继续配置。
创建结果不明确时不自动重建，需在本机核对。更新用途只影响新任务，不改变已有任务。

管理员只管理通过自己创建的助手，不接管原有机器人、不修改密钥或扩大允许名单。
管理消息经过单独的持久化入口，不会作为普通业务任务交给具有本机完整访问权的 Codex 执行。
管理机器人本身仅申请消息收发能力；业务助手按原创建流程申请基础办公能力。
无需保持浏览器面板打开，但本机 Bridge 必须持续运行。

## 群里的任务管家

在飞书页点“创建任务管家”，用自己的飞书扫码创建。把它加进普通群，由扫码创建者第一次 @它说出需求，Bridge 自动为这个群建立连接和处理规则，这条消息会直接开始执行。其他人不能替创建者接入新群；群内其他成员接好后也可以 @它派活。

任务管家根据用途挑本群已经接入的业务助手，按需要拆分任务、同时派活、回答追问并收齐结果。它只发现和调用本群助手，已有协作授权仍生效；未授权时通知创建者确认。群内闲聊和机器人发言不会自行触发任务。移入别的群时，同样需要创建者发起第一条 @ 请求。

## 接入已有机器人

在飞书页面点击“接入已有机器人”，或在“添加群配置”中选择已有应用。在目标群 @机器人发送配对码，然后为该群选择项目、填写 Prompt 并保存。群消息要求同时满足：
群已允许、明确 @ 当前机器人；群内所有成员无需逐人配对。私聊仍要求发送者已允许。未开启话题协作的旧群，回复续接仍只允许原发起人在原会话中操作。

### 普通群内协作

在「群配置 → 编辑本群配置」开启「群内协作」。新建群用途的助手默认申请所需权限并开启；已有群不会自动改变。将私聊助手接到新群时，面板会沿用它的业务用途并改为群交付规则。

- 直接使用普通飞书群。助手像群成员一样在群主聊天中发言，不创建话题回复、不要求打开话题侧栏。首次 @ 开始任务，回复相关消息可继续，其他成员也能补充；群内未指向机器人的闲聊不触发任务。
- 每个话题有一位负责人；同时 @多个已启用话题协作的机器人时，以消息中第一个有效机器人为负责人。其他机器人不会重复派同一单。
- 不同群、不同根消息分别保存话题；私聊不会接入群任务。新发起的独立消息创建新话题；沿用旧话题时保留原项目和业务规则。
- 助手使用实际协作工具派任务、说明进展、向委托者提问并等待答复。每个执行任务最多 24 条讨论，仍受三层委托、八个子任务和原有协作授权限制。授权不会因为一起出现在群里而自动扩大。
- 子助手提出问题后，即使当前一轮执行结束，也会保留等待状态；委托者答复后自动恢复原任务和原会话。等待答复不占用执行名额，也不会当作已完成的分工交付。
- 群内发言用简短的大白话，只说必要的问题、结果和实际困难。接单、等待、完成等常规状态保留在面板，不自动向群里重复通报。
- 已绑定到本群的协作机器人以自己的身份在群主聊天中发言；参与被委托工作不要求开启免 @ 接收权限。未绑定的助手由负责人明确注明「由负责人转述」。最后由负责人在本群汇总交付。机器人消息本身不触发新任务，避免互相循环。
- 群成员在执行中补充的要求会排入同一任务，当前步骤结束后接续处理；不会抢占正在执行的步骤。
- 保存时实际检查 `im:message.group_msg`（接收群聊中所有消息事件）及消息读取权限。只有 @消息权限不足以支持免 @续聊；缺少时显示具体权限和当前应用的后台地址，不会静默扩大旧应用授权。收到群消息也只处理已 @开始的话题及其回复。
- 讨论与消息引用有独立的持久记录，发送使用固定去重编号；临时服务故障保留待接收消息，重启后继续。历史任务与历史消息不补跑、不迁移。

## 接收图片、视频、语音和文件

支持文字、富文本图文、图片、视频、语音和文件。接收器以当前机器人的身份下载原消息的附件，保存到本机私有目录，再把文件路径、大小和校验值交给 Codex。图片需实际查看，音视频和文档由 Codex 使用适用工具或业务 Skill 读取；接收成功不等于已完成转写、理解或交付。

- 私聊可直接发送附件；需要延续已有要求时，回复自己之前的任务消息发送附件。图文消息里的说明和图片会一起交给 Codex。
- 群内图文消息需 @机器人。纯图片、视频、语音或文件无法同时 @时，可回复本人先前已 @机器人的任务消息发送。不会捕获未明确指向机器人的普通群附件，也不能把其他成员的任务接走。
- 原消息附件下载需要消息读取权限及原消息访问范围，`im:resource` 不替代这项权限。平台接口接受 `im:message`、`im:message:readonly`、`im:message.history:readonly` 之一。若后台找不到只读项，搜索“获取与发送单聊、群组消息”（`im:message`）；开通后需发布生效并重新发送附件。新助手申请只读权限；已有可用等效权限的应用无需重复申请。
- 单个附件最多 100 MB，单条最多 10 个附件、合计最多 256 MB。更大的素材请发当前机器人可访问的云端链接。消息合并转发和表情包资源暂不支持，需拆开发送原文件。
- 下载失败会自动有限重试并在原会话给出原因；附件未就绪时不会提交一个缺文件的 Codex 任务。重复事件和重启会复用已保存的附件，不重复派单。
- 助手管理员负责管理用途；媒体素材请发给对应业务助手。不会因此给管理员开放普通业务执行权限。

历史上被旧接收器忽略的媒体消息不自动重放。更新后请发送一条新消息验证。附件存储于每个应用状态目录下的 `attachments/`，权限为本机用户私有，不包含在插件分享包中。

飞书后台选择长连接，订阅 `im.message.receive_v1`，启用机器人并发布应用。
私聊使用 `im:message.p2p_msg:readonly`，群聊使用 `im:message.group_at_msg:readonly`，
回复使用 `im:message:send_as_bot`。同一个应用的其他长连接可能分流事件。
新版不需要卡片回调订阅。

每个群分别编辑 Prompt，必须恰好包含一次 `{{message}}`。修改项目或 Prompt 只影响新任务；回复已有任务仍沿用创建时的项目和规则。

不同飞书主体分别添加应用凭据；同一应用的多个群共用一条接收连接，不重复启动接收器。
现有配置直接显示为第一份群配置，无需重新配对。应用设置中的私聊规则独立于各群，私聊用户默认不开放。
停用群只影响该群接收新消息，停用应用则影响该应用所有群；已经提交到 Codex 的任务不因此取消。
默认 Prompt 不添加强制人工审核。示例：

```text
飞书任务：{{message}}

根据消息完成工作，按需调用已安装的 Skill。
完成后说明结果；缺少必要信息或超出授权范围时询问我。
```

## Codex 模型

Bridge 优先使用 Codex 桌面应用自带的运行程序，新任务沿用 Codex 保存的默认模型；无需在飞书页重复选择。某个聊天临时切换的模型不等于全局默认模型。已有任务续接使用原会话的模型。
如显式配置 `CODEX_BIN`，则使用指定程序；该程序需支持当前账号和模型。

## 后台服务

`./scripts/install-daemon` 安装 `dev.codex.bridge.v2`，端口 8797。
数据默认保存在 `~/Library/Application Support/CodexBridgeV2/`，日志位于
`~/Library/Logs/CodexBridgeV2/`。`./scripts/uninstall-daemon` 仅停用后台服务。
直接运行 `run.sh` 使用插件目录下的 `data/`。不要同时启动两个实例占用同一端口。

Codex 以 Full Access、无需命令审批的策略执行；飞书允许名单应只包含可信任用户。
面板仅监听本机回环地址。密钥仅保存在本机；公开仓库不含凭据和用户数据。
不要在日志或聊天中粘贴连接密钥。已由 Codex 桌面占用的任务可能无法由独立
Bridge 进程恢复，面板会显示原因；此版本不声称解决跨进程任务所有权问题。

## 助手之间协作

在业务助手卡片点击「协作助手」，选择它允许调用的其他助手。授权是单向的，对这个助手接入的私聊和群任务生效；默认没有互相调用权限，助手管理员不参与业务协作。已导入的旧机器人不自动进入这个名单。

所有新业务任务会获得本机调用入口；原业务 Prompt、飞书凭证、历史任务不被改写。可按先后顺序调用，也可一次把独立任务分给多位助手。目标使用自己的工作目录和已保存的默认助手规则（群专属规则不作为其他助手调用的默认规则）。子助手返回内容或本地文件，主助手负责核对、发布云端资料和在原飞书会话统一回复；不会让多个子助手给各自的群发消息。

- 每批最多 3 项委托，整棵主任务调用树最多 8 项；每个深度最多 2 个协作任务执行，等待下一层不会占满下一层的名额。
- 支持 A → B → C，最多向下 3 层；不能调用自己或调用链中的上级。
- 任务详情展示主任务与子任务的关联及状态。主助手必须收取结果再结束，否则标为失败，不冒充已汇总成功。
- 请求编号保证重试不重复派单。状态和调用关系保存在 SQLite；重启后读取原任务，不盲目重发不确定的操作。
- 等待接口每次最多等 60 秒；pending 表示仍在运行，不能当成失败后重建任务。子任务失败或需要处理会原样交回主助手。
- 取消授权或停用目标会阻止还没开始的委托。已经执行的任务不会被粗暴终止，返回结果仍供原主任务核对。
- 调用凭证限定到一个活动主任务，只返回该任务的结果；身份来自实际飞书入站记录，不能由消息正文冒充。配置入口仍仅限本机。

助手页面支持切换「自由协作」和「逐次确认」。自由协作允许当前 Bridge 中已接入且启用的业务助手直接分工，使用各自已有能力，不发协作码或逐次确认；任务管家仍仅调度同群助手。停用、移除、循环和调用数量限制仍生效。新建的业务助手就绪后也自动纳入，不需要重复勾选。关闭自由协作后，原有明确授权保留。

逐次确认模式下，也可以直接在飞书说「请让研究助手找核查助手一起完成」。未提前授权的调用会暂停，Bridge 私聊可核实的创建者。直接回复「允许本次协作」或「拒绝本次协作」，不需要复制编号或打开面板。同时有多件事待确认时，回复对应的协作请求即可；系统不会猜测你指的是哪一件。临时授权仅对当前主任务有效，15 分钟未确认会失败。拒绝会原样返回给委托者。旧通知中的协作码仍兼容。

同一助手管理员创建的助手可通过管理员确认一次；其他情况由来源助手和目标助手各自的创建者在各自机器人中确认，不能用不同应用的 Open ID 猜测是否为同一个人。重名需提供准确 ID。消息正文、其他助手的回复均不能自行赋予权限。

本功能沿用本机 Codex 的执行权限，不是面向互不信任租户的操作系统隔离沙箱；不同主体之间是否允许协作，由本机操作者显式设置长期授权，或由可核实的创建者确认本次协作，不自动互通。

开发验证：`python -m unittest test_assistant_collaboration`。真实 Codex 验收使用 `scripts/verify-assistant-collaboration.py`：在 artifacts 内创建隔离目录和模拟入站记录，真实执行并行及串行调用，不创建飞书机器人、不发送飞书消息。

多层与临时授权验收：`scripts/verify-assistant-nested.py`，使用真实 Codex 执行 A → B → C 和并行任务，隔离模拟飞书入站及创建者确认，拦截通知，不向真实用户发送测试消息。
